# AI Coding 一年实战

## 从效率幻觉到能力进化

- 基于文章阅读与个人思考的分享
- 关键词：瓶颈、Spec、验证闭环、并发、能力进化

---

# 一个反直觉的开场

## 你以为变快了

- 开发者主观感受：更快
- 实验客观测量：反而变慢
- 真问题不在“AI 有没有用”
- 真问题在“AI 加速了哪个环节”

> 核心钩子：局部加速，不等于系统提效

---

# 为什么会出现悖论

## 编码加速了

- 需求理解没有同步提速
- Code Review 带宽没有同步增加
- 测试验证仍然需要成本
- 上下文切换开始吞噬收益

右侧视觉建议：

- 一条 SDLC 流程线
- 编码节点高亮为蓝色
- Review 节点高亮为红色

---

# 第一结论

## 瓶颈不在写代码

- AI 更像“编码工位加速器”
- 团队真实瓶颈常在 review 与验证
- 非瓶颈提速，可能只会制造堆积

大字金句：

> 系统吞吐量由瓶颈决定，不由最快的环节决定

---

# 别先焦虑选框架

## 框架名很多，本质很像

- OpenSpec
- Superpowers
- BMAD
- Spec Kit

结论：

- 它们都在沉淀可复用工作流
- 差别更多是封装方式与使用风格
- 重点不是“选哪个”
- 重点是“你是否理解底层模式”

---

# 全文最重要的概念

## Spec / Rule / Skill

| 概念 | 本质 | 回答的问题 |
| --- | --- | --- |
| Spec | 业务知识 | 要做什么 |
| Rule | 工程规范 | 约束是什么 |
| Skill | 工作流 | 具体怎么做 |

演讲强调：

- 很多团队把三者混在一起
- 混用之后，AI 的表现会明显变差

---

# 为什么 Spec 不能省

## AI 不会自动替你理解业务

- 它会读代码
- 但不等于它真的理解上下文
- 尤其在存量系统、兼容场景、复杂规则里
- 跳过 Spec，返工率通常会上升

一句话总结：

> Spec 不是负担，而是让 AI 从“猜意图”变成“理解约束”

---

# 为什么 Skill 比 Rule 更有效

## 因为高信噪比

- Rule 常驻上下文，容易过长
- 不相关规则会稀释注意力
- Skill 按需加载，更聚焦
- 相关指令靠近任务，遵循性更好

视觉建议：

- 左：冗长 Rule 列表，灰色
- 右：单个任务 Skill 卡片，蓝色高亮

---

# 给 AI 一根安灯绳

## 生成之后，必须自动验证

- Lint 拦基础错误
- Unit Test 拦边界条件
- E2E 拦关键路径断裂
- Review 拦深层设计问题

闭环：

> generate -> verify -> fix/log

---

# 单任务变慢，不是核心问题

## 关键在于你能否并发

- 完整流程下，单任务可能更慢
- 但 AI 可复制，可多会话并行
- 你可以从“执行者”转向“调度者”
- 前提是验证闭环足够可靠

讲述重点：

- 并发不是多开窗口
- 并发是可验证、可控、有限 WIP 的协作

---

# 但并发也有边界

## 不要把堆积扩大化

- PR 不能过大
- 同时 review 的任务不能太多
- reviewer 带宽才是最终约束
- 推荐并发度：2 到 3 更现实

金句：

> 并发加速生成端，WIP 限制保护下游端

---

# 真正值得记住的一章

## 有了洗衣机，你可能只是在洗更多衣服

- AI 让你写更多代码
- 但不一定让你更轻松
- 苦差事不会消失，只会换一种形式
- 从“手写重复代码”变成“管理 AI 产出”

思辨点：

- 如果只是产出更多代码，那只是线性提效
- 如果能做以前做不到的事，才叫能力进化

---

# 文章最强的落点

## 把省下来的时间投向复利

- 更系统地读源码
- 更深入地读论文与报告
- 建立自己的 Spec / Skill 资产
- 提升架构判断与验证能力

大字收束：

> AI 的真正红利，不是更快写代码，而是重定义你做什么

---

# 最后的实践建议

## 从甜点区切入

优先交给 AI 的任务：

- 文档初稿
- 测试用例草稿
- commit message
- 日报周报
- 重复性高、可校验的工程杂务

谨慎交给 AI 的任务：

- 支付
- 金额计算
- 高风险核心链路

---

# 我的总结

## 这篇文章最值得学的，不是工具清单

- 而是它把讨论抬到了系统视角
- 从“写代码快不快”
- 变成“流程瓶颈在哪里”
- 再到“工程师该如何升级自己的能力结构”

结束页短句：

> 用 AI 省下时间，然后去做以前做不到的事

---

# Q&A

## 可以讨论的三个问题

- 你的团队瓶颈真的在 coding 吗？
- 你现在有没有稳定的 verify 闭环？
- 你省下来的时间，最后流向了哪里？
