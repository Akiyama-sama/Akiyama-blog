## 0. 一句话结论

选题成立,而且**差异化位置已经被生态自己腾出来了**:

1. **现有 pi / dsh 的代码评审扩展全部是"交互式、会话内"的**(supi、pi-review 面板、pi-review-loop…),没有任何一个做成"服务端 webhook 形态、评审结果贴回 PR/SARIF"。而独立开源评审器(pr-agent 13.4k★、alibaba/open-code-review 47.5k★、kodus、reviewdog)又**都不是 harness 扩展**。→ **论文的定位:"把自动代码评审重构成 agent harness 扩展,并带上服务端 webhook 模式"** 正好落在两边交叉的空档。
2. **技术路线有工业+学术双重背书**:"确定性管线夹住 LLM"(Meta RADAR ✅ 2605.30208、阿里 OCR ✅)是被验证过的形态;RepBench ✅(AST+PDG 83.2% vs 源码 53.5%)+ "LLM 自己做程序分析很差" ✅(2505.12118)构成"AST 只是原料、LLM 只能在结构化表示之上做仲裁"的完整论证链——**这直接支撑课题技术栈里"AST 分析 + 静态工具 + LLM"的选型**,比厂商宣称硬得多。
3. **提升空间有公开量化锚点,不用自己造 benchmark**:c-CRAB ✅ 现有评审 agent 合计仅解决 ~40%;SWE-PRBench ✅ 只检出人标问题的 15–31%。评测集(MCR-Bench / SWR-Bench / SWE-PRBench / MetaLint / SecCodeBench-V2)全部现成可跑。

## 3. 静态分析 / AST 工具链:核实过的一学期规模装配

✅ 全部命令 flag 从 --help/官网/README 实录核对(版本会漂,**答辩附录务必钉版本**):

```text
substrate   tree-sitter(27.2k★ MIT;CST≠AST:含全部 token 节点、错误恢复可解析半成品——
            正好用于"LLM 提议的编辑未必合法"场景)
规则层      ast-grep(16.3k★ MIT)`run` vs `scan`,`scan --format=sarif` 直出标准格式;
            规则配置 sgconfig 用 camelCase;官方 ast-grep-mcp(479★)已把 AST 搜索暴露给 agent
            Semgrep CE(17.1k★ LGPL)安全/正确性规则,--sarif;⚠ 跨文件 taint 在专有 Pro 二进制里
每语言补    Ruff --output-format sarif / ESLint+@microsoft/eslint-formatter-sarif / PMD / Bandit(按目标语言取)
指标层      lizard(无 --json,用 Python 库 API;Sonar 认知复杂度实现)+ jscpd(kucherenko/jscpd,v5 Rust 引擎)
SCA         OSV-Scanner v2:`scan source -r --format sarif`;pip-audit
交换格式    SARIF 只在边界用;内部统一自定义 Finding 记录
CodeQL      只当对照组:queries 仓 MIT,engine CLI 单独条款——"perform academic research" 对开源合法,
            私有仓 CI 不行;输出 `--format=sarifv2.1.0`(没有 sarif-2.1.0 这种写法)
跳过        SonarQube(server+DB+scanner 不是一个学期)、Semgrep Pro、Trivy/Grype、jQAssistant
```

三个设计级要点:

1. **Semgrep CE 的边界 = 论文卖点**:社区引擎只做函数内/单文件,跨文件 taint 属 Pro。诚实框定为"**Agent 在 OSS 引擎做不了的过程间推理层做仲裁**",这是可辩护的贡献,不是缺陷。
2. **severity 映射是脏活,可直接写成"统一 Finding 模型"小节**:词表互不保序——Semgrep `ERROR/WARNING/INFO`、ast-grep 默认 `hint`、**PMD priority 1 才是最严重(反的)**、Bandit 是 severity×confidence 二维要塌成一维、CodeQL 三档 `@problem.severity` + 0–10 `@security-severity`,而 SARIF `level` 只有 `none|note|warning|error`——`recommendation/hint` 映射不当就**静默消失**于 GitHub 的 High/Medium 分诊视图。内部 Finding:`tool/ruleId/severity_raw/file/line/endLine/message/cwe/autofix?` + 双射映射表 + `properties` 透传。
3. **许可与坑**:真规则库是 `semgrep/semgrep-rules`(Semgrep Rules License,**非 LGPL**;`semgrep-community` org 不存在),打包进毕设要单独声明;pyan3 是 GPL-2.0(`--text`,README 原话就是给 AI agent 用);madge 作者是 pahen、flag 是 `--circular`(没有 `--detectCircular`);sarif-tools 调用名就叫 `sarif`,子命令 `codeclimate`;gitleaks 的 `detect` 已废弃→`git/dir/stdin`;trufflehog 用 `--results=verified,unknown`;**没有 canonical 的 tree-sitter call graph,要自己搭**;snakeviz 是 runtime profiler 不是静态调用图。

## 4. 平台集成:GitHub Actions 有一个**必须改设计的日期**

✅ docs.github.com 全 200 核实(2026 文档大重组,老路径 301 到新结构):

- ⚠ **GitHub 默认策略封锁公开仓库的 `pull_request_target`,2026-11-02 起强制执行**(现为 evaluate 模式;私有/内部仓不受影响)。→ **毕设主路径必须设计成官方两段式**:`pull_request`(不可信、只读 token、无 secret;clone+diff+跑 pi 评审)`upload-artifact` → `workflow_run`(可信、可写;下载 artifact 贴 review / 传 SARIF)。文档自带完整示例 YAML;跨 run 下载 artifact 要 `run-id: ${{ github.event.workflow_run.id }}` + `github-token` + `actions: read`。**答辩演示放自己的私有仓最省事。**
- 细节约束:`workflow_run` 的工作流文件必须在默认分支、`workflows:` 过滤匹配 **name 不是文件名**;链式最多 3 层;fork PR 的 `pull_request` payload 为空;check runs 建在 PR commit 上要 `head_sha: github.event.pull_request.head.sha`;**Checks API 对 fork push 的 `pull_requests` 数组为空**;annotations 50/请求、1000 同名 check run 上限;`permissions: code-quality` 已存在(键名清单核实)。
- **SARIF 上传**:POST `code-scanning/sarifs`,body 只有 `commit_sha/ref/sarif/checkout_uri/started_at/tool_name/validate`——**旧博客的 `start_sha`/`validate-urls`/`tool-names` 已不存在**;gzip+base64;10MB gzip 上限、单 run 25k results **只留按 severity 排序的前 5000**;202 异步要轮询 `sarif_id`;`github/codeql-action/upload-sarif@v4`(现值 v4),输入名**下划线 `sarif_file`**,多文件必须给 `category`;`ref/sha` **对 fork PR 一律忽略**→必须可信 workflow 传。PR 内显示条件(官方原文):**告警标识的全部行都在 diff 内、且属于新增/修改行**。
- `gh pr review -a/-c/-r/-b/--body-file` 核实存在;github-script 现 @v9、方法挂 `github.rest.*`、防注入=值走 `env:` 不进脚本插值;**"dummy commit 贴 status"是社区都市传说,官方无文档,论文别写**。

## 5. 结构化输出层:方案里一个默认假设要改

✅ providers 官方文档当日核实:

- **"forced tool_choice 逼 JSON"正在被废弃**:Claude Opus 5.5 / Sonnet 5.5 / Fable 5.1 上 `tool_choice: any|tool` **直接 400**;官方替代 = **structured outputs**(`output_config.format`,已 GA、无需 beta header;旧 beta header 值现名 `structured-outputs-2025-11-13`,**`-09-24` 查无实据别引**)。⚠ Anthropic 的 enum 大小写**不保证**且无报错——`severity` 枚举必须大小写不敏感比较。语法编译有硬上限(20 strict tools / 24 optional params / 16 union)+ 180s 超时;grammar 缓存 24h,改 schema 结构=缓存失效+首请求延迟。
- **schema 子集互不兼容**(这就是论文"跨 Provider 可移植性矩阵"素材):OpenAI 支持递归 `$ref`、`minimum/maximum`、`minItems>1`,但要求全字段 required + `additionalProperties:false`,不支持 `allOf/not/if`;Anthropic **不支持递归 schema 和数值边界**,`minItems` 只认 0/1;Gemini `additionalProperties` 可给 schema(独家)。→ **数值约束放 Pydantic validator,不放 wire schema**。
- **DeepSeek 官方只有 `json_object`,且自认"偶尔返回空 content"** → dsh/国产模型路线必须配 retry-with-feedback(instructor 机制:ValidationError 文本回灌为 user 消息)或本地 constrained decoding(outlines 16k★ / guidance 21.8k★——两家现在都走 llguidance/outlines-core 语法编译,注意 `model(prompt, Schema)` 返回的是**字符串**,仍要 validate)。**Qwen 百炼有 `json_schema`+`strict`**(参数面核实,强制机制未核 ⚠)。
- instructor 归属敲正:**`567-labs/instructor`**(14,026★,jxnl 重定向至此);推荐入口已是 `instructor.from_provider("openai/…")`,`patch()` 降为 advanced。json_repair canonical 是 **`mangiucugna/json_repair`**(5,118★;`mariostoev/python-json-repair` 404)。

## 6. 推荐架构(论文第 3–4 章的骨架)

```text
GitHub/GitLab 事件(webhook 或 Actions 两段式)
  → clone + diff(只读、当数据处理)
① 确定性扫描    Semgrep CE / ast-grep / 每语言 linter / OSV-Scanner → SARIF/rdjson(统一 Finding)
② LLM 评审      pi extension headless(--print / --mode rpc,--tools read,grep,find,ls)
                证据注入(文件+调用关系+规则命中)→ 多角色 finder → 验证器 gate(要证据才留)
③ 融合          确定性优先 + FNV 指纹去重 + finding 生命周期状态机(ACTIVE/RESOLVED/SUPPRESSED)
④ 报告          reviewdog(14 reporters)+ SARIF upload + GitLab Draft Notes;CI gate 用 exit code
```

理论支柱(✅ 全部重验 ID):固定管线胜自主循环——Agentless(2407.01489,本地化→修复→验证,cents 级成本);分阶段评审工业范本——Sashiko 11 阶段("证明不了就不报"的 FP gate);外部验证器必须存在——CoVe 2309.11495 / CRITIC 2305.11738 / Self-Debug 2304.05128,以及**负结果 2310.01798**(无外部反馈的"自我纠错"反而降准确率;常被误写为 2310.01796,那是 LILAC)。
编排选型:**固定 DAG 不上 LangGraph**;首选 **Pydantic AI(21k★,`output_type=` 类型级校验)**或 asyncio+Pydantic 手搓状态机;LangGraph 写成"评估过、因不需要 resume/HITL 未采用"的论证段。AutoGen 已实质归档(README CAUTION;PyPI 冻在 0.7.5)→ 后继 Microsoft Agent Framework。MetaGPT `ext/cr/` 有现成 **points_cn.json 中文规范规则集**,rule-grounded 审查可直接引(✅ 2308.00352)。

### 上下文注入与检索层(RAG,✅ 当日 HF config/GitHub API/arXiv 逐条核)

核心决策:**PR 评审的上下文主体是"diff hunk + 外层函数 + 文件头",不做整仓语义索引;跨文件影响分析用精确索引而非向量相似度。**

- 依据一:最强的 OSS 评审器 pr-agent **根本没有 embedding 索引**——`extra_instructions` + `repo_context_files`(自动读 `AGENTS.md`/`CLAUDE.md`,默认分支,`repo_context_max_lines=500`)+ dynamic context(hunk 向外扩到外层函数/class)。(⚠ 旧配置 `max_score` 在现仓已不存在,别写。)
- 依据二:**Better Call Grep ✅ 2601.23254**——免索引词法检索(ripgrep 式)在仓库级补全上与语义 RAG 打平,索引的构建/维护成本常常不值;SWE-bench 系任务由 agentic grep/Read 解决。
- 依据三(反向需求):跨文件要的是**精确**——LSP 3.17 的 `references` / `callHierarchy`(方法名 spec 核实)+ **SCIP**(✅ 精确索引、无需跑编译器;仓库已迁 `scip-code/scip`)。参考实现:**aider repo map** ✅(读源码核实:文件依赖图上 **plain `nx.pagerank` + personalization**(不是 personalized_pager),tree-sitter Query 抽 def/ref,当前码路不用 universal-ctags;`--map-tokens=1000` 预算内贪心填充)——"**token 预算下的上下文选择器**"就照这个做,是 ② 段的现成设计蓝本。
